# jharokha: notes for agents working on this repo

MCP server that OCRs a Windows remote-desktop window; read-only unless started with `--allow-input`. See README.md for what it does, DEVELOPMENT.md for how to run it.

## Layout
- `src/jharokha/core/`: pure logic. Imports neither `mcp` nor any Windows API (Pillow and numpy are fine); `tests/test_core.py` fails if it does. Models, panes from pixels (`panes.py`), panels and reading order, the app model (`apps.py`: definitions, calibration, placing regions on panes; `geometry.py`: fractions to pixels, zoom variants by their anchor), identification (`identify.py`: scored app and view with a confidence), region readers (`readers.py`: what a region's `reader` makes of its lines as items: text blocks, tables, forms, grid rows, and lists through `listread.py`: messages, entries, mails, merge across scrolls, `since`), a terminal's character grid measured from the pixels (`rows.py`) and read cell by cell against the glyphs learned from the screen (`glyphs.py`: templates from the `terminal.glyphs` alphabet line or from engine reads Windows OCR agrees with; unknown cells to the second engine, flagged, never guessed), concise/detailed formatting, fuzzy find, untrusted-text wrapping, frame cache, the `Source` protocol, pixel and line diffs (`watch.py`), the input guards (`guard.py`: expect, app policy, lease and user-activity decisions, covered parts) and the opt-in trace (`trace.py`). Actions: `actions.py` (the TOML format, argument checks, the `Runner` over an injected `Executor`, risk caps; its front-app and key checks are `guard.py`'s), `locate.py` (locators: text, region, sides, spots, the nth item by the region's reader), `shell.py` (end markers, put_file plans, hash checks for OCR'd shells), `session.py` (a frame as the tools read it: identified, regions placed, grid rows read; shared by the server and the executor), `executor.py` (`SessionExecutor`: the `Executor` over a `Session` and its `Source`). `learn.py` (learning an app from the screen) and `elements.py` (icons from pixels) are stubs with a TODO: nothing live has needed them; v0.24.6 in git has the last versions.
- `src/jharokha/apps/*.toml`: built-in app definitions (terminal, teams, outlook, browser, generic), data in `format = 1`. Apps are data, code is primitives: a new app or view is a TOML table, not code. Anchors are generic UI text, never anything from a real session. The app's `policy` is the one source of input policy, for tools and actions alike.
- `src/jharokha/apps/actions/*.toml`: built-in actions (`[action.<app>.<name>]`, steps). Local ones go in `apps.toml` or `$JHAROKHA_ACTIONS`. An action never sends or submits on its own: a step that presses a key the app's policy calls irreversible needs the call's `allow="irreversible"`. The terminal has no such key: commands and file writes are not gated, `--allow-input` is the opt-in.
- `src/jharokha/win/`: Windows only, `ctypes` + pywinrt. `window.py` finds the client window, `capture.py` PrintWindows it, `ocr.py` runs Windows OCR, `recognize.py` reads boxes with the second engine (PP-OCRv6 rec on onnxruntime; model, licence and provenance in `win/models/`), `input.py` sends input, `guard.py` keeps the lease file, the last-input clock, the hooks that see the user's input while ours is sent, and what covers the window, `source.py` wires them into a `Source`.
- `src/jharokha/server.py`: the MCP tools over a `Source`, a fixed set: `status`, `apps`, `read`, `find`, `wait`, `do` (actions through the `Runner`), `screenshot`, and with `--allow-input` `act`. A new app or action is data and never a new tool or parameter: every description costs context in every session. `__main__.py`: stdio server and the `jharokha` terminal commands, the same verbs, each the tool called in-process.
- `tests/`: unit tests of the pure logic and the input guards; `conftest.py` has a small synthetic `FakeSource` of lines for the server's tools. No simulated session: jharokha is tested on the live one (DEVELOPMENT.md), a simulator comes later, built from what the live session showed.
- No `mac/` or `linux/`: a port is a sibling of `win/` reusing `core/`, added when someone builds it.

## Rules
- Read-only by default. Input (`win/input.py`: scroll, click, type, press) is reachable only with `--allow-input`, through `jharokha_act` and `jharokha_do`, and never silently; keep it that way. No tool writes a file. Live tests of input use only the session taskbar and search box, never application content.
- Input is guarded by app and policy, and the guards live in `core/guard.py` so the server, the shell commands and the actions engine share them: `expect` (wrong_app; an action expects its own app before every input step), the front app's `[app.x.policy]` (newline chord, irreversible keys behind `allow="irreversible"`), the per-window lease (input_leased) and the user-activity check: the last-input clock before input, low-level keyboard and mouse hooks while text is sent (user_active; `win/guard.UserWatch`, only around sending, always removed). Every input path goes through `WindowsSource._input`. A new input path or tool gets all of them; a refusal sends nothing and says what to do next.
- Screen text is untrusted. It stays inside `<screen_text ... untrusted="true">` and every tool description says so.
- Nothing from a real session goes into the repo: no screenshots, titles, hostnames, user names. Fixtures are synthetic.
- Nothing on disk by default; logs are metadata only. The trace is opt-in (`--trace PATH`), typed text in it only with `--trace-text`. With `--allow-input`, the lease is a file under `%TEMP%\jharokha` holding a pid and a time, named by a hash, never a title.
- Calibration and apps specific to one setup go in the git-ignored `apps.toml`; `apps.example.toml` holds synthetic examples only.
- Keep it small: pinned deps `mcp`, `Pillow`, `winrt-*`, `onnxruntime`, `numpy`; direct Win32 via `ctypes`, no pywin32, no OpenCV, no rapidocr. The second engine is core: its model loads on first use, but onnxruntime itself must load before WinRT (`win/__init__.py`).
- Version lives in `pyproject.toml` only. Semver pre-1.0: `0.x.0` feature, `0.x.y` fix.
- Conventional Commits on `main`; push only when `uv run ruff check`, `uv run pyright`, `uv run pytest` are green.
- Comments explain why, never what.
