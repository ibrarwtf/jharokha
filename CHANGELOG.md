# Changelog

## v0.30.0

Reads across scrolls are joined at an anchor, and a gap between them is reported (Pomerado's list cursor keeps an anchor and the recent rows' keys, and says when the list changed under it).

- `listread.item_key`: kind, side, sender or title, the clock of the time (so `Today 10:44` and `10:44` agree), and the first 40 characters, folded.
- `listread.merged` finds the anchor first: the newest of the last 16 items collected that the read below holds with the same key, where each key occurs once. What the read below shows above the anchor is already collected; only the anchor and what follows it are matched item by item, so nothing below the anchor can be pulled back onto an older item that merely reads alike. Without an anchor, every item is matched as before.
- A collecting scroll counts the reads that shared no item with the read before: `fields.gaps` and a `warning` that items between them may be missing (the list moved more than a screen).

## v0.29.0

Two looks before items are trusted (Pomerado returns a value only once two looks 500 ms apart agree).

- `jharokha_read` as items, and an action's `read` step as items, look at the screen a second time 0.3 s later. An item the second look reads differently (a list still drawing, a half-scrolled row, an OCR misread of a moving frame) carries `unsteady: true`, and the head says `unsteady=N (read differently a moment later: read again)`. When the pixels did not change, the second look costs a capture and no OCR. The answer is still the first read, so verified lines and `since` work as before.
- `readers.key` is the one item key, for `since='last'` and the second look alike.

## v0.28.0

What an input did is judged by what is new since it (Pomerado counts only elements new or changed after an action).

- `jharokha_act`'s `until` text or regex counts only on lines that are new or changed since the input: a line with the same text in about the same place before (within 4 px, `watch.fresh`) does not count, so a prompt or a "Saved" already on screen no longer ends the wait at once and reports success the input never had. A line that moved (a terminal that scrolled) counts. When the wait times out with the text on screen only where it was before, the error says so. `gone` and `ready` are unchanged.
- The terminal's end marker already worked this way: its token is new for every command.

## v0.27.0

An ambiguous text target is refused, not guessed (Pomerado ranks a picker's matches and refuses a tie).

- A locator's text that matches more than one line is ranked: the whole line, the line's start, whole words inside it, part of a word. When two or more share the best rank and no `nth` is given, the locator misses with "ambiguous: N matches alike; nothing was picked", the lines it matched as candidates, and what to add (nth, a region, more of the text). It used to click the first in reading order. A single best match still wins: `Ana Alder` clicks the chat entry, not the preview line `Ana Alder: see you then`. A regex target matching twice is ambiguous.
- This applies wherever a locator does: `jharokha_act` targets, action click steps and `jharokha_find` with a locator. `jharokha_find`'s plain query still lists every match.

## v0.26.1

- The end marker is no longer missed when the row above it ends in the token's first two letters (`...KX` above `KX7R4C:True:0`): the two rows joined read as the command's echo split over two rows, so the marker counted as part of the echo and the run waited out its timeout. Nor when the marker's own letters sit within one of an echo (`73XXXX:` holds `73`, a gap, and `XXX:`). A marker row is never taken for the echo now. Found by a test that failed for one random token in about 500; 30,000 random tokens pass now. A likely part of the missed markers of 0.25.4's report.

## v0.26.0

Waits say why they ended (an idea from Pomerado's waits, which name their outcome).

- `Screen.settle` returns how it ended: `still` (quiet long enough) or `max` (still changing when the time ran out), with the frames looked at, how many changed and how long it had been quiet. A screen that never held still used to read the same as one that did.
- `jharokha_act`'s head says `settle=max (still changing: N changes)` after `settled_ms` when the screen never held still; `jharokha_wait` returns `ended` (`appeared`, `gone`, `ready`, `still`, `max`) and `looks`, and its timeout says how many looks it took. An action's `wait for = "settled"` step notes the same.

## v0.25.7

- `jharokha_wait(seconds=N)`: a plain pause of up to 300 s that reads nothing. Agents used a wait for a text that never appears as a timer.
- An action's input waits up to 60 s for the user's keyboard and mouse to go idle (3 s without input) before it is refused with `user_active`, where it waited 10 s: a read that only brings Teams forward, or a command, is queued behind the user rather than refused into retries. `jharokha_act` keeps 10 s.

## v0.25.6

- `terminal.write_file {path, text, shell}`: a text file written as readable lines, no base64. The lines are typed in batches of up to 3,000 characters into a list in the shell (PowerShell or bash), each batch confirmed by the list's line count, then joined with the text's own line ending (LF or CRLF), written as UTF-8 without a BOM, and its SHA-256 checked against the one sent. A batch cuts the list back to where it starts, so a batch typed again after a misread confirmation adds its lines once. Tabs go in as expressions (a typed tab would complete a file name); PowerShell's curly single quotes are doubled like `'`. Other control characters, and a line too long for one batch, are refused before anything is typed. The generated commands are tested by running them in this machine's PowerShell and bash, each batch twice, against the exact bytes.

## v0.25.4

From a day of use by an agent in another session, where about a third of `terminal.run` calls came back with "no end marker within 30 s" for commands that had finished. Checked on synthetic screens only so far; still to be checked live.

- `terminal.run` takes `timeout_s`, up to 300 (default 30). A step's `timeout_s` may name an argument; a number argument may have a `max`.
- On a timeout, `output` holds what the command printed so far and `fields.finished` is false, so a slow command's result can be read without a screenshot. Before giving up, the view is scrolled to its bottom once and looked at again: a view scrolled up does not follow new output, so its marker can sit below it.
- Output longer than the screen is read back up the scrollback: when the reply fills the screen from top to bottom and its own line is not on it, the view is scrolled up five notches at a time, each page joined to the rows below where they overlap (`…` where they do not), until the command's line shows or the view stops moving; then scrolled back down.
- A sent line must show in the shell before Enter is pressed. If it does not within 2 s (a paste that came in empty), it is cleared with Escape and typed once more; if that does not show either, nothing is run and the step fails with "did not show". An Enter alone used to leave the run waiting 30 s for a marker that never came.
- The font is learned on first use: `terminal.run` runs the `terminal.glyphs` alphabet first when fewer than 60 glyphs are known for the terminal on screen. A reply with more than 20 cells no glyph matched carries a `warning` to run `terminal.glyphs` again.
- `terminal.put_file` confirms a chunk by its stored length when OCR misread its index (the marker's token is the chunk's own), and a chunk that is still not confirmed says what was read after the marker.

## v0.25.2

- The risk scheme is gone: no `risk` on steps, no `max_risk` on actions, no `allow` of read, reversible or irreversible capping them, no `safety` list in results. Every command had been "irreversible" since 0.24.5, so every call carried the flag and it guarded nothing, and "reversible" on a terminal step would have been a lie. The terminal has no such key: commands, the alphabet run and `put_file` run under `--allow-input` alone. About 100 lines fewer.

## v0.25.0

A terminal is read by matching its cells against glyphs learned from the screen, not by OCR. A terminal draws one font at one size on a fixed grid, and the RDP codec leaves its glyphs nearly untouched (measured live: the same glyph in two places differs by 0.01, the nearest other glyph is 2 away), so each cell is a nearest-neighbour lookup over about a hundred templates: exact where OCR confused `l`, `I` and `1` or `O` and `0`, and tens of milliseconds for a screen where the second engine took seconds.

- `core/glyphs.py`: cells cut on the grid `core/rows.py` measures, each compared as its ink against its own background (so foreground colours and inverse video read as the same glyph); a template store per font and size; a cell no template is close to goes to the second engine for that run of cells, is counted as unknown in the read's header (`unknown_cells=N`), and becomes a template when Windows OCR read the row the same way. A read whose cells all sit far from the templates means the grid drifted, and the grid is searched back onto its cells.
- `terminal.glyphs`, a built-in action: prints the printable ASCII alphabet (two lines, nothing else) and learns every glyph from it. Once a session before terminal work; again after a zoom or font change. Without it the templates build up from engine reads, a screen or two slower.
- `terminal.run` polls with an exact read every 0.1 s: the end marker is never left to Windows OCR, and no row of a result is. The 500-cell engine budget, pending rows, the engine's row alignment and shape heuristics are gone (`rows.py` keeps grid calibration only: about 600 lines fewer).
- Measured live on the Windows 365 session, in one server process: `terminal.glyphs` 2.4 s; 12 lookalike rows 12/12 exact in 1.9 s where the budgeted engine read returned 8/12; a 12-row table 12/12 in 2.0 s; 40 rows of output in 1.9 s; one-liners 1.5 to 1.8 s (6.2 s before); a full-screen read 73 to 99 ms (0.9 s before).

## v0.22.2

- Fix: an app whose definition has no `[app.x.policy]` (every app `jharokha_learn` made, one written by hand, an anchored table of an old layouts file) had no input policy, so Enter in its reply box sent and a typed newline was Enter.
